Music Store Network

A semester-long capstone where I built a working branch network for a fictional music store, connected it to other store locations, added a searchable inventory system, and helped build a failover design that kept the network available if a main switch stopped working.

YEAR2026
ROLEBranch build + Stage 4 collaboration
FOCUSNetworking, Linux, services, redundancy

[01] CONTEXT

What was I building?

The project was based on a fictional music store with multiple locations. Each student represented one store branch and had to build the technology that branch would need to communicate with the rest of the company.

My branch included a client computer, a server, an Ubuntu router, and physical Aruba switches. The project started with basic connectivity and later added communication with other branches, Internet access, a web-based inventory search, security controls, and network redundancy.

In simple terms: I built one store's network, made it communicate with other stores, and then helped make sure the combined network could survive a switch failure.

[02] GOAL

What needed to work?

A user at one branch needed to be able to use the network without knowing anything about the infrastructure behind it. The finished environment needed to give devices the correct network settings, connect them to local and remote systems, provide Internet access, and allow store inventory to be searched across connected branches.

The final stage added another requirement: if the main network switch failed, a backup switch needed to take over automatically so users could stay connected.

[03] TOOLS

What did I use?

  • VMware Workstation: ran the Ubuntu client, server, and router virtual machines.
  • Aruba 6300 switches: connected devices and moved traffic between parts of the network.
  • DHCP: automatically gave devices their IP address and gateway settings.
  • OSPF: allowed network devices to share information about how to reach other networks.
  • VRRP: created a backup gateway that could take over if the main switch failed.
  • nftables / NAT: controlled traffic and allowed internal devices to reach the Internet through the Ubuntu router.
  • Apache + PHP: hosted the inventory website.
  • MariaDB: stored the music store inventory data.

[04] DESIGN

How did it work?

The client represented an employee's computer. The server hosted the inventory website and database. The Ubuntu router connected the branch to other networks and provided Internet access.

The client and server did not connect directly to the Internet. Their traffic passed through the Ubuntu router, giving me one place to control how traffic entered and left the branch.

OSPF allowed the routers and switches to learn which path to use when traffic needed to reach another branch. Later, VRRP gave the network a shared virtual gateway so a backup switch could take over if the primary became unavailable.

[05] BUILD

How the project grew

STAGE 01

Build the branch

I created the Ubuntu client, server, and router virtual machines and installed the software needed for networking, web services, database services, firewalling, and troubleshooting.

STAGE 02

Make the network communicate

I connected the branch to the Aruba switches, configured automatic IP addressing, set up the Ubuntu router, enabled Internet access, and used OSPF so the branch could learn how to reach other networks.

STAGE 03

Add the inventory system

I configured MariaDB and hosted a PHP inventory website with Apache. Users could search inventory using details such as instrument type, condition, and price. The application used a read-only database account.

STAGE 04

Add failover

My partner and I connected our completed networks, adjusted the Aruba switch configurations, and added VRRP. We deliberately removed the main switch from service and confirmed that the backup switch took over the gateway role.

[06] TROUBLESHOOTING

What went wrong?

Not everything worked on the first try. One early problem was getting the Ubuntu router to communicate with the rest of the network. I checked the interface settings, IP address, next hop, and routing table until I found where communication was breaking down.

I also had situations where the client could communicate locally but could not reach the Internet. That pushed me to check the entire path: the router's forwarding settings, firewall rules, NAT, and the route toward the upstream network.

When OSPF was involved, I learned that entering a configuration was not enough. I needed to confirm that the devices had actually formed a neighbor relationship and learned the expected routes.

Stage 4 introduced another challenge: two networks that worked independently did not automatically work together. My partner and I had to compare VLANs, trunks, routes, and VRRP settings and make changes so the combined design behaved as one network.

[07] TESTING

How did I prove it worked?

I tested the environment throughout the project rather than waiting until the end. I checked that the client received the correct network settings, verified communication between the client, router, and server, and tested Internet access.

I used traceroute to see the path traffic was taking. For OSPF, I checked neighbor status and the routing table to confirm the branch was actually learning how to reach other networks.

The final validation was the failover test: my switch normally stayed in the backup role, became the active gateway when the primary was removed, and returned to backup after the primary recovered.

[08] SECURITY

How was it protected?

The client and server were not given their own direct Internet connections. Their traffic passed through the Ubuntu router, where nftables controlled forwarding and NAT.

VLANs separated logical parts of the network, SSH was used for remote administration, and the inventory website used a read-only MariaDB account. That meant the application could retrieve inventory without needing administrative database permissions.

VRRP also improved availability by reducing the risk of the primary gateway becoming a single point of failure.

[09] REFLECTION

What did I learn?

My biggest lesson was how important time management is in technical work. Even with an entire semester, progress depended on limited switch availability, other students finishing their configurations, collecting the required screenshots, and getting each stage inspected before moving on.

I learned to prepare before I had access to the equipment, ask questions earlier, and keep track of what still depended on another person or resource. I also became much more comfortable troubleshooting. A failed connection stopped feeling like proof that everything was wrong and became information I could use to narrow down the problem.

Stage 4 also changed how I thought about collaboration. It was not just about splitting tasks. My partner and I had to compare our configurations, agree on changes, and test two independently built networks as one system.
